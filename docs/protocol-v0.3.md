## 0. 一句話

v2.1 的合成題目對這一級的方法已經飽和，而且有矛盾標註，分不出 E4B、26B、GD1、GLiNER 誰比較強。
v0.3 照 jevlike `data/HARD_GUIDE.md` 的寫法，做一批**每段文字都有單一可判定狀態**的難題。目標是用預先寫死的階梯規則，分出這四者的能力落差，並決定本機判讀層要用哪一個。

## 3. 資料

### 3.1 題目定義：先判單段狀態，再由兩段推導是否改變

- **S（單段狀態，主任務）**：給一段文字，四選一判斷專案目前狀態。每段有一個 gold。
  - A 按計畫（on track）、B 延後（delayed）、C 卡關（blocked）、D 取消（cancelled）。
  - 選項文字沿用 v2 的 `labels`（同語同詞），順序固定為 A–D。
  - 題目統一為「依據目前文字，專案現在最符合下列哪一種狀態？」，只寫肯定形。
- **P（變更，衍生任務）**：由 S 的段落組成 old/new 配對。gold 為「是否改變」= `gold(old) ≠ gold(new)`，另記「改成哪一類」。
  - 正例：每一對孿生題（同一 `pair_id`、gold 不同），以編號較小者為 old。
  - 負例：Q6 改寫子集中，原段落對兩種改寫版本各組一對（狀態相同）。
  - P 的 gold 完全由 S 推導，**不再另外標註**，避免 v2 T6-word 那種「說改了，但文字沒改」的矛盾。
- **判定規則**：撰寫者、盲判者與**所有 arm** 看到同一份規則與「今天」的日期。規則接在題目後面，作為 `instructions` 的一部分（NLI 無法接收題目，這是它的限制）；「今天」放在段落第一行。確切字串見 analysis-plan。規則如下：
  - 以**最新**的明確狀態陳述為準。
  - 條件式（「若下週沒回覆則延期」）在條件尚未發生前，判斷**目前**狀態。
  - 「取消」只算本專案；其他專案或子項目被取消，不算本專案取消。
  - 已排除的阻礙不算卡關。
  - 日期以文中給定的「今天」為準。
- 撰寫完成後若發現規則有漏洞，只能改規則再重新覆核全部題目，不能個案處理。

### 3.2 難題型（中英各半；題量依 [檢定力估算](../results/power-v3/summary.md)）

前五型照 jevlike 撰寫規範，後五型是專案狀態特有的：

| 代號 | 題型 | 例子（簡化） | 預期誰會掉 |
|---|---|---|---|
| H-inc | `incomplete`：資訊不完整，但仍可判定 | 只寫「供應商說最快下季」，沒寫交付日 | 小模型 |
| H-bor | `borderline`：兩個狀態的邊界，靠一個關鍵事實決定 | 延後但仍在合約寬限期內 → 按計畫 | 全部 |
| H-noi | `noisy`：錯字、口語、縮寫、中英夾雜 | 「API 那包 blk 住了，等 vendor」 | EG2、NLI |
| H-dis | `distractor`：混入無關的負面資訊 | 別組的阻礙、已關閉的舊工單 | GLiNER、EG2 |
| H-inv | `inverted`：先講結果再講原因，或用「不是 X，是 Y」 | 「不是延期，是範圍縮小後提前交付」 | 小模型、NLI |
| H-imp | `implicit`：沒有狀態關鍵字，要推論 | 「測試環境要等資安審查，審查排在下個月」 | 全部 |
| H-res | `resolved`：聽起來負面，其實沒事 | 「上週卡住的金流串接，昨天已經打通」 | GLiNER、EG2 |
| H-tmp | `temporal`：多段更新、前後矛盾，以最新為準 | 週一卡關、週三已排除、週五又因新問題卡關 | 全部 |
| H-dat | `date`：要比較日期才能判斷 | 今天 11-12、預計 11-25、截止 11-20 | 非生成式方法全盲 |
| H-lng | `long`：超過 512 tokens，狀態句埋在中段 | 會議紀錄全文 | MediaPipe 的三個 backend |

- **H-dat 做兩版**：原始日期一版；另一版用 jevlike input-guide 的寫法，把比較結果寫在括號裡，例如「（預計交付晚於截止日 5 天：是）」。兩版共用 gold，只在 Q4 比較。
- **孿生題**：每型至少 15 對（30 段），同一對只改**一個事實**就翻轉 gold，共用 `pair_id`；其餘 30 段獨立。
- **label 分布**：每型中，A–D 各至少 10 段。A（按計畫）不得超過 40%，避免「全猜 A」也拿高分。
- **題型群組**：推論與判讀以群組為單位，單一題型只報準確率與 95% CI，不做「明顯掉」判讀。

  | 群組 | 題型 | 每型段數 | 測試 n |
  |---|---|---|---|
  | G1 語言表面 | H-noi、H-dis、H-inv | 60 | 120 |
  | G2 推論 | H-inc、H-bor、H-imp、H-res、H-tmp | 60 | 200 |
  | G3 結構 | H-dat、H-lng | 90 | 120 |

- **總量**：8 × 60 + 2 × 90 = **660 段**。另加 H-dat 先算好版 90 段，以及 Q6 改寫子集 100 段 × 2 種說法。
- **題量依據**：見[檢定力估算](../results/power-v3/summary.md)。
  - 整體測試集約 440 題，對 8 點差距的檢定力約 0.97。
  - 群組測試集 ≥ 120 題，對 10 點差距約 0.83。
  - 單一題型的測試集只有 40–60 題，10 點差距也只有 0.2–0.4 的檢定力，所以不做推論。
  - 真實差距剛好 5 點時，任何題量的檢出率都約 0.5，這是「觀察差距 ≥ 5」規則本身的限制。

### 3.3 撰寫規範（照 jevlike `data/HARD_GUIDE.md`，以下為不同之處）

1. **先定 gold，再寫情境**。每段附一句 `rationale`。
2. **段落只放證據，不放結論**：不得出現選項文字，例如「專案已取消」「進度落後」直接當結論；可以描述事實，例如「客戶來信終止合約」。
3. **不得留下與 gold 衝突的狀態句**。這是修正 v2 T6-word 的關鍵。
4. **手寫，不用模板**：同一型內，句型、專案名、人名、日期都要有變化。骨架沿用 v2 的五種：週報、ADR、工單、會議紀錄、PRD。
5. **規則基線先寫**：照 jevlike `data/rules/` 的格式，寫 10–20 條關鍵字規則當基線。規則要在難題之前寫好，不能針對難題調整。
6. 欄位如下：

```json
{"id": "s-h-imp-001", "task": "status", "lang": "zh", "skeleton": "weekly", "hard_type": "implicit",
 "state": "...", "gold": "C", "pair_id": "s-h-imp-p01", "today": "2026-11-12",
 "variant": null, "rationale": "測試環境被資安審查擋住，審查排在下個月，目前無法推進"}
```

### 3.4 Gold 覆核（kill criteria）

已定案（2026-11-12）：Claude Code 撰寫；另一個 Claude 實例盲判全部題目；不做人工抽查。

- **撰寫者**：執行本規格的 Claude Code session，依 §3.3 撰寫。
- **盲判者**：另開一個 Claude subagent，與撰寫者不共用上下文；建議用與撰寫者**不同的 Claude 模型**，以降低錯誤相關。
  - 盲判者只拿到 `state`、`today`、題目、選項與 §3.1 的判定規則。
  - 看不到 gold、`rationale`、`hard_type`、`pair_id`，也看不到同一對孿生題的另一半。
  - 題目打亂順序後分批送出。盲判者的提示詞在凍結時一併存檔。
- **不一致的題目**：撰寫者不得直接改 gold。
  - 先由第三個 Claude 實例裁決：看得到兩邊的答案與理由，但看不到 `hard_type`。
  - 裁決後仍無共識的題目刪除，並在 MANIFEST 記錄刪除數量與原因。
- **已知限制**：撰寫者、盲判者、裁決者都是 Claude 家族，可能共有同一種誤讀，覆核只能抓到「同一模型換個上下文就不同意」的錯。報告要寫明 gold 未經人工覆核。Claude 不在比較名單內，所以沒有「自己出題自己考」的問題。
- **整體不一致率超過 10%，代表規則或題目有問題**：先修正再凍結，不得進入評分。
- 改寫子集（Q6）的每種說法，都由同一位盲判者覆核 gold 是否不變。
- 覆核紀錄寫進 `data/synthetic-v3/checks.jsonl`，比照 v2 的 `check_llm` 流程。

### 3.5 切分與凍結

- 依 `pair_id` 切分：**校準集 1/3、測試集 2/3**。所有門檻、溫度、組合規則只在校準集上決定。
- 凍結 `data/synthetic-v3/{status,pairs,rules}.jsonl`、`manifest.json`（SHA256）、`analysis-plan.json` 後才能跑任何 arm。凍結後要改資料就開新版。
- 若 Phase 1 的真實文件到位，另做 100 段真實子集（人工標註，不進 git 時放 `data/private/`），只報告、不調參。

- **J 系列**：用 jevlike 既有的四選一介面讀第一個 token 的機率，不改 `decide/prompt.py`。E2B、E4B、26B 吃同一個 prompt 字串，全部開 `--swa-full`，帶 `<bos>`（jevlike v6）。
- **P 的兩種做法**：
  - 推導：兩段各自判斷，比較 argmax，或用 1 − Σ P(old=k)·P(new=k) 當連續分數。
  - 直接：沿用 v2.1 的 paired 題。
- 所有 arm 的選項順序固定為 A–D。Q6 才另外做順序置換。

## 5. 指標

1. **S 準確率**：整體、每個群組（G1–G3）、每個難題型、每種語言。
   - 95% CI 用依 `pair_id` 的配對 bootstrap（1,000 次）。
   - 差異檢定用 exact McNemar，只在整體與群組層級做。
   - 單一題型與單一語言只報準確率與 CI。
2. **孿生題雙對率**：同一對兩段都答對的比例。
3. **P**：
   - 準確率：門檻在校準集上決定。
   - AUROC：專屬負例。
   - 固定誤報率下的召回：誤報率 0% 與 1%，門檻在校準集上決定，**測試集上報告實際誤報率**。
4. **校準**：每個 arm 在校準集擬合一個溫度，在測試集報告 ECE 與 Brier。
5. **一致率（Q6）**：同一題的兩種說法加上兩種選項順序，四次 argmax 全同的比例。
6. **覆蓋率**：被拒或截斷的題目數，記 null，不填零。截斷也要標記，因為 EG2、Laya 截斷時不會報錯。
7. **錯誤偵測**：用原始信心預測「這題會不會錯」的 AUROC，比照 jevlike v3。

## 6. 假說與判讀規則（凍結時一併寫死）

判讀規則沿用 jevlike v3 的定義：

- **「明顯掉」**：差距 ≥ 5 個百分點，且 McNemar p < 0.05。
- **「相當」**：CI 重疊，且 p ≥ 0.05。

| # | 假說 | 成立 | 不成立 |
|---|---|---|---|
| H12 | 測試集整體：J-26B 比 J-E4B 明顯高；各群組另行判讀 | v0.3 有鑑別力；26B 的分數可以引用，並列出哪些群組分得出 | **v0.3 也飽和**：記錄哪些群組飽和，再加難一版，不得宣稱 26B 比較強。檢定力只足以檢出 ≥ 8 點的整體差距，差距在 5–8 點之間未過時要寫明「檢定力不足」，不寫「相當」 |
| H13 | 某題型 J-E2B ≥ 0.95 | 該題型對這一級太簡單，從群組判讀中剔除後重算 | — |
| H14 | DM-GLiNER 在 G1 + G2 合併後，與 J-26B 的差距 95% CI 上限 < 5 點 | GLiNER 可以當本機單邊判讀器，取代 D2；26B 只處理 G3（日期與長文件） | 判讀層用 26B；GLiNER 最多當前置篩選 |
| H15 | H-dat 先算好版比原始版：J-26B +≥ 8 點 | 日期比較一律程式先算，與 jevlike v23 一致 | 26B 會自己比較日期；R 規則降為備援 |
| H16 | GD1 比 J-26B 明顯高，且 Q6 一致率 ≥ 0.9 | GD1 可以當覆核層（低信心題送雲端） | GD1 只當上限參考，不進管線 |
| H17 | P 的推導做法 ≥ 直接做法（各 arm 分別判讀） | 管線改成「單段判斷 + 比較」，可以快取每段的結果 | 保留直接比較兩版的做法 |
| H18 | 校準集的門檻搬到測試集後，實際誤報率 ≤ 2 倍目標 | 門檻可以上線前用少量資料校準 | 門檻要在真實資料上重做 |

kill criteria：

- 若 §3.4 的不一致率超過 10%，不進入評分。
- 若規則基線在測試集上 ≥ 0.85，代表題目被關鍵字解掉，要先加難。

## 8. 執行順序

1. §12 待決事項定案 → 寫 `data/synthetic-v3/analysis-plan.json` → 凍結本文件（記錄 commit 與 SHA256）。
2. 先寫規則基線，再依 §3 撰寫 660 段，加上 H-dat 先算好版與改寫子集。
3. 執行 §3.4 覆核 → 修正或刪除 → 凍結資料 manifest。
4. smoke：每個 arm 跑 10 題，確認輸出格式、option mass、`<bos>`、512 視窗的處理方式。
5. 跑 CPU arm → GPU 的 J 階梯 → GD1。每題落盤，可續跑。
6. 在校準集上擬合溫度與門檻並鎖定 → 跑測試集報表 → 依 §6 判讀。
7. 跑成本表。
8. 若有真實子集，只報告。
